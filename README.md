# Davnoot Digital

Independent growth agency — marketing site (static HTML/CSS/JS).

Deeper docs live next to this file: [BLOG.md](BLOG.md) for the blog engine and the
`/seoteam` dashboard, [ANTISPAM.md](ANTISPAM.md) for the lead-form defences.

> **There is deliberately no `build` script.** Vercel serves this repo as a static
> site with zero build step. `npm run site` and `npm run bundle` are run locally
> and their output is **committed**. Adding a `build` script changes how Vercel
> resolves the output directory and breaks the deploy.

## IndexNow — instant indexing for Bing (and therefore ChatGPT)

[IndexNow](https://www.indexnow.org) is a free, open protocol with no signup and no
paid API. One POST tells every participating engine that a URL just changed:

**Bing · Yandex · Naver · Seznam · Yep**

**Google does not participate.** This does not replace `/sitemap.xml` or Search
Console — it sits beside them. What makes it worth wiring up anyway is Bing:
Bing's index is a primary retrieval layer for ChatGPT Search, so the gap between
"published" and "quotable by an answer engine" drops from days to minutes. Treat
it as an AEO tool, not an SEO one.

### Setup — one manual step, then it runs itself

**1. Generate a key.** [bing.com/webmasters](https://www.bing.com/webmasters) →
**IndexNow** → generate. You get a hex string like
`a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6`.

**2. Commit the key file.** Create a file at the **repo root** named `<key>.txt`
whose entire contents are the key itself, and nothing else:

```bash
echo -n "a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6" > a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6.txt
git add a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6.txt
```

This file is what proves we own the domain. It is a plain static asset — **not** a
route, **not** generated by a script — served at
`https://www.davnoot.com/<key>.txt` with `text/plain` from its `.txt` extension,
exactly like `robots.txt`. Nothing in `vercel.json` shadows it: redirects run
before the filesystem and none matches a root `.txt`, and the `/:slug` catch-all
rewrite runs *after* the filesystem, so a real file always wins. `scripts/indexnow.test.js`
asserts all of that, and asserts the file's contents match its own name — a
mismatch is a **403 on every submission**.

**3. Set the key in two places.**

| Where | What | Used by |
| --- | --- | --- |
| Vercel → Settings → Environment Variables → **Production** | `INDEXNOW_KEY` | the CMS write routes |
| GitHub → Settings → Secrets and variables → Actions | `INDEXNOW_KEY` | `.github/workflows/indexnow.yml` |

Optionally add it to `.env.local` too, for running the CLI by hand.

**4. Backfill once.** Nothing has been submitted before, so send the whole sitemap
one time:

```bash
npm run indexnow:ping -- --all
```

That is the entire setup. If the key is not set, every ping silently no-ops — the
site behaves exactly as it does today.

### What pings what

| Change | Pinged by | URLs submitted |
| --- | --- | --- |
| Blog post published / edited / unpublished / deleted | `api/seoteam/posts/*` | the post URL, plus `/blog` when a post enters or leaves the listing. A slug change submits **both** the old and the new URL. |
| Composed or marketing page published | `api/admin/pages/[id]/publish.js` | that page's canonical URL |
| Composed page deleted | `api/admin/pages/[id].js` | that page's URL, so the engines recrawl and drop it |
| A root `.html` page edited **in code** | `.github/workflows/indexnow.yml` | whatever `/sitemap.xml` shows changed since the previous deploy |
| Anything, by hand | `npm run indexnow:ping` | whatever you pass it |

Two things deliberately do **not** ping:

- **Draft saves** (`PUT /api/admin/pages/:key`). The editor autosaves every 900ms
  and drafts are invisible to crawlers; pinging there would submit the same URL
  hundreds of times per session and get the host throttled.
- **Scheduled publishes** with a future date. The page is not live yet. It is
  picked up by the CI sitemap diff on the next deploy.

### The CI workflow

`.github/workflows/indexnow.yml` runs on every push to `main`. It exists because
the root `.html` marketing pages are edited in code and shipped by a deploy — no
request handler is involved, so no API hook can see them.

It diffs the live `/sitemap.xml` against the previous run's snapshot
(`actions/cache`) on `<loc>` + `<lastmod>` pairs and submits only what changed,
including URLs that **left** the sitemap. The sitemap is the right source of
truth: `api/sitemap.js` already applies the archived / noindex / `sitemap.include`
exclusions, so anything it omits is something we do not want indexed.

It knows the deploy is live by waiting for the production sitemap to stop matching
the snapshot — no Vercel token, no webhook, no guessed sleep. A commit that changes
nothing indexable waits out the timeout and correctly submits nothing. The very
first run has no snapshot to diff, so it takes a baseline and submits nothing;
that is what step 4 above is for.

> **A caveat worth knowing.** A root `.html` page only shows up in the diff if its
> `lastmod` moved, and that comes from `compiledAt` in `lib/compiled-pages.gen.js`
> / `lib/sitemap-static.js`. So editing a page and committing **without running
> `npm run site`** leaves the sitemap unchanged and nothing is pinged. That is the
> same discipline the golden test already enforces — but here the failure is
> silent, so reach for `npm run indexnow:ping -- <url>` if you ever bypass it.

### The CLI

```bash
npm run indexnow:ping -- /blog/my-post /services/seo   # specific URLs (paths or absolute)
npm run indexnow:ping -- --all                         # every <loc> in the live sitemap
npm run indexnow:ping -- --all --dry-run               # print, submit nothing
npm run indexnow:ping -- --key <k> /some-page          # override INDEXNOW_KEY
```

Unlike the API routes, the CLI does **not** gate on `VERCEL_ENV` — you are running
it against production deliberately. It exits non-zero if a submission is rejected.

### When something is wrong

Everything is fire-and-forget: a failed ping logs and is dropped, and can never
turn a successful publish into a 5xx. So the logs are the only place failures
surface. In Vercel's function logs, look for `[indexnow]`:

| Log | Meaning | Fix |
| --- | --- | --- |
| `submitted N URL(s) — 200` | working | — |
| `403 REJECTED` | the key file is missing, misnamed, or its contents do not match | confirm `https://www.davnoot.com/<key>.txt` loads and contains exactly the key |
| `422 REJECTED` | the submitted URLs are not on `www.davnoot.com`, or the key mismatches | check `SITE_URL` in `lib/templates.js` |
| `429 rate limited` | too many submissions | usually means something is pinging in a loop |
| nothing at all | `INDEXNOW_KEY` unset, or not a production deploy | both are required; see `skipReason()` |
